2. **Catalogue premise:** there's no single unified catalogue module today — model metadata is spread across `ollama.ts` (`SUGGESTED_OLLAMA_MODELS`), `llamaCpp.ts` (`LLAMA_CPP_MODELS`), whisper tiers, and parakeet variants. "Extend the existing catalogue" likely means *introducing* a unified structure; Open Question #4 already acknowledges this.
3. **Sizing:** scope spans catalogue types + new TS provider + new Rust command + UI + release pipeline + security — well past a reviewable single change. Recommend stacked PRs (types → Rust probe/command → provider wiring → UI → release metadata).
4. **Open Question #1 is the linchpin:** the chosen sidecar defines the transcribe/probe stdio contract, arg construction, and metadata format the Rust command + provider depend on. Milestone-1 (types, opt-in UI showing "unknown") can proceed without it, but the live-transcription acceptance criterion cannot. Scope M1 to exclude live transcription, or pick a default sidecar.
5. **Verification gap:** the Commands section defers targeted test commands. The repo already uses vitest (`*.test.ts`); name the runner (`pnpm test`) so the "provider-selection tests" criterion is executable.
6. **`supportsStreaming`:** Verbatim's flow is press-to-talk → transcribe-on-stop (batch); streaming ASR may not map to the current pipeline, so treat this as metadata-only for now.
7. **Minor:** the `ModelCapability` type omits `supportsDiarization` though the probing section mentions diarization.

None of these require a human to resolve before code is written; all are recoverable during implementation or at PR review.
