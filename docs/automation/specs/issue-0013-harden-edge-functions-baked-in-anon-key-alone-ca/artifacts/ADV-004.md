## Findings

**NON-BLOCKING (advisory)**

1. **Anonymous-user farming weakens per-user rate limits.** An attacker with the anon key can still call `signInAnonymously()` repeatedly to mint fresh JWTs, defeating per-user caps. Mitigation: lean on Supabase's built-in per-IP anon sign-in rate limit (`config.toml` shows `anonymous_users = 30`) and/or CAPTCHA, and keep IP as a secondary rate-limit key. The core win (anon key alone no longer reaches Azure) still holds. Tunable at implementation/PR review.

2. **Pre-transcription duration enforcement is non-trivial.** Azure returns `duration` only *after* transcription. True server-side duration caps require decoding audio in Deno; the pragmatic proxy is the body-size cap. The spec already hedges ("decoded or declared duration"; "422 or 413 depending on implementation") — acceptable to leave to the implementer.

3. **Rate limiting is optional per acceptance criteria** ("rate limiting exists… OR a documented strict stopgap"). Since durable counters need a schema change (gated under "Ask first"), the implementer can ship JWT + caps first. Consistent with the issue treating rate limiting as fix #2. Fine.

4. **Existing error-leak to fix in passing.** `transcribe/index.ts:20-22` returns `e.stack` in the 500 body; the spec's non-leaky error rule covers this — good to enforce.

5. **File structure nit.** The spec file wraps its content in a `Proposed content for … ```markdown` fence rather than being the raw spec. Cosmetic; content is complete.

6. **Dashboard enablement of anonymous sign-ins** is a deploy-time operational step (Open Q#3), explicitly authorized by the issue and gated by the required human merge review — not a code blocker.

No requirement is self-contradictory, misreads the issue, or demands a maintainer-only decision before code is written. Concerns are recoverable during implementation and PR review.
