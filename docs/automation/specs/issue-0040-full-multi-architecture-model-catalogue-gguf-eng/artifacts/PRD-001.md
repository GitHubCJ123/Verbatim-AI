## Original issue

Future work split out from #23.

## Gap
The catalogue work (#31) shipped **bring-your-own-GGML discovery** + a compact quantized large tier + a data-driven abstraction. But Verbatim still only runs **Whisper (ggml) + Parakeet (onnx)** engines. It does NOT have Handy's real model breadth — Canary, Voxtral, Qwen3-ASR, Moonshine, GigaAM, Granite, SenseVoice, etc. (Handy ships ~65 models across ~13 ASR architectures).

## Why it wasn't done in #23
Handy loads all of those through a single **GGUF, multi-architecture engine** (a `transcribe-cpp`-style loader that auto-detects architecture from the GGUF header). Verbatim deliberately avoids **in-process whisper.cpp linking** because it hit bindgen/libclang version-mismatch issues on Windows (this constraint shaped the whole P0 engine pivot to a persistent `whisper-server` sidecar). A multi-arch GGUF engine would reintroduce that linking risk.

## Proposed approach (to design)
- Evaluate a **GGUF multi-architecture engine as a sidecar** (so no in-process linking), analogous to how `whisper-cli`/`whisper-server` are downloaded prebuilt runtime binaries. Candidates: a `transcribe-cpp`-style server, or per-architecture ONNX runtimes via sherpa-onnx.
- Extend the data-driven catalogue (already in place from #31) with per-model architecture + **GGUF-metadata capability probing** (languages / streaming / translate / lang-detect).
- Keep it opt-in and non-regressive; Whisper + Parakeet remain the defaults.
- Handle release-pipeline bundling of any new sidecar per platform/GPU variant.

## Non-goals
- No in-process whisper.cpp/GGUF linking (keep the sidecar model).

Blocks full closure of the model-breadth part of #23's original intent ("large support for new models").
