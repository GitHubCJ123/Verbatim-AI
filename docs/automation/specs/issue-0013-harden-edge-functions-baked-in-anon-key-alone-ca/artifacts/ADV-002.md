## Spec Review — Issue #13 (Harden Edge Functions)

I grounded this against the repo. The spec's stated facts check out: `supabase/functions/{transcribe,cleanup}/index.ts` exist and have **no in-code auth check** (they rely on the gateway, currently bypassed by `--no-verify-jwt`); `src/lib/ai/index.ts#getAuthHeaders` does send the anon key as bearer in local mode; the Supabase client uses `persistSession/autoRefreshToken` (so `signInAnonymously()` is viable); `pnpm test` (vitest), `pnpm lint`, `pnpm build` all exist. The spec correctly reads the issue's intent (preferred fix #1 anonymous sign-ins + caps + optional rate limiting) and meets the completeness bar (objective, acceptance criteria, files to change).

### Findings

**NON-BLOCKING (important — surface to implementer):**
1. **`verify_jwt` alone will NOT reject the anon key.** The Supabase anon key *is* a valid project-signed JWT (`role: anon`), so re-enabling gateway JWT verification still accepts it. The function code must inspect claims and reject non-authenticated identities (e.g. require `role === 'authenticated'` / a real `sub`; anonymous users have `is_anonymous: true`). The spec's acceptance criteria and the test "`Bearer <anon key>` is rejected" already force this, but the *mechanism* should be stated so nobody ships a gateway-only solution.
2. **Rollout ordering / backward-compat.** Flipping off `--no-verify-jwt` immediately 401s already-shipped clients that still send anon-key-bearer. Coordinate: release the anonymous-session client first (or force-update), then redeploy. Keep sending the `apikey` header (gateway still needs it).
3. **Existing 500s leak internals.** Both functions currently return `e.message + e.stack` in the body (`msg.slice(...)`). The spec forbids leaking stack traces — implementer must also fix this pre-existing behavior, not just new paths.

**NON-BLOCKING (advisory):**
4. **Server-side "max audio duration" is non-trivial** — the function doesn't decode audio; duration is only known from Azure's response *after* transcription. Practical guard pre-Azure is the body-size cap; treat duration as a post-hoc/body-size proxy rather than over-scoping a decoder.
5. **Body-size cap for transcribe**: `req.formData()` buffers the whole body; check `Content-Length` early so the 25 MB cap rejects before buffering.
6. **Anonymous-user row accumulation** in `auth.users` is a data-growth/privacy follow-up; consider periodic cleanup of stale anonymous users (operational, out of scope here).
7. **Cosmetic**: the spec file nests the entire spec inside a `Proposed spec content … ```markdown` fence. Content is complete and readable.

**No BLOCKING findings.** Enabling anonymous sign-ins and redeploying with JWT verification are exactly what the issue authorizes, so they aren't maintainer-only decisions. Open questions all ship with sensible recommended defaults, and the strong post-spec safety nets (draft PR, PR reviewer, lint/test/build, human merge) cover the rest.
