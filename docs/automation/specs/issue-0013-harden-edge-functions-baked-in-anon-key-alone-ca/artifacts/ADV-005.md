## Findings

**NON-BLOCKING (advisory), high-importance:**
1. **JWT verification alone will NOT reject the anon key.** The anon key is itself a valid project-signed JWT (`role: "anon"`), so removing `--no-verify-jwt` still lets anon-key bearer requests pass the gateway. To satisfy the "anon-key-only rejected" criterion (and test #3), the functions must additionally inspect claims — reject `role: "anon"`, require `role: "authenticated"` (anonymous sign-in users carry `role: authenticated` + `is_anonymous: true`). The spec's own test encodes the correct end-state, so this is recoverable at implementation, but the implementer must not just flip the flag.
2. **Persist `verify_jwt = true` in `supabase/config.toml`** (per-function) so verification survives future deploys, not just the one-off omitted flag.
3. **Duration cap is only enforceable pre-Azure via body-size proxy** — the webm container isn't decoded server-side and Azure returns `duration` only *after* transcription. Spec's flexible wording ("where available") accommodates this; body-size is the practical lever.
4. **Rollout sequencing**: redeploying with verification before clients ship anon-session support (and any already-installed older clients) will break local-mode calls. Handle via draft-PR/staged rollout; worth an explicit note.
