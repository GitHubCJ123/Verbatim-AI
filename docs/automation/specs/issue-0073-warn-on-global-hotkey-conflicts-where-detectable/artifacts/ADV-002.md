**NON-BLOCKING (advisory):**

1. **Windows stale-vs-external distinction is the real technical crux.** The current code swallows *anything* containing `"already registered"`. The plugin's internal same-app `AlreadyRegistered` (raised by its own map) is likely a *different* error than the OS-level `RegisterHotKey` failure when another app owns the combo. The implementer must inspect the actual error variants in `global-hotkey 0.7.0` / `tauri-plugin-global-shortcut 2.3.1` rather than assume both surface as the string `"already registered"`. If they prove indistinguishable, surface that finding rather than silently degrade. Acceptance criterion #2 + the proposed tests guard this.

2. **Error-model wiring gap.** `set_hotkey` returns `Result<(), String>`. Returning structured `{kind, message}` as `Err` means the frontend `catch (e)` at Settings.tsx:582 receives an object; its `e instanceof Error ? e.message : String(e)` would render `"[object Object]"`. Implementer must update that catch to read `e.kind`.

3. **macOS reserved-list matching needs normalization.** The list uses `Cmd+Space`/`Cmd+Option+Esc`, but app specs use `CommandOrControl`/`Control`/`Alt`. Matching must normalize modifier aliases and be order-insensitive to avoid false negatives/positives — an explicit normalization helper is warranted.

4. **Apply the macOS reserved-check at the save/validation layer, not solely `register()`.** The fn/right-⌘ sentinel returns early before registration, and macOS registration doesn't fail on conflicts anyway. Also gate the reserved-list to macOS so it never warns on Windows/Linux.

5. **Frontend test hedge can be firmed up.** vitest + existing `.test.ts` files exist, so the mapping unit test should simply be added (not left conditional).

These are all resolvable during implementation and covered by the downstream PR review + verification safety nets. The open questions carry conservative recommended defaults and are low-stakes.
